# restart-guard-v12：已知 P0 / P1 问题（临时测试说明）

在本轮真实运行环境测试中，发现两个需要优先修复的问题。当前版本暂时保留用于社区交流和问题验证，预计完成修复后更新测试版本并撤下本说明。

## P0：默认配置下模型切换可能被错误拒绝

**影响：** 默认配置下，即使会话尚未接近上下文窗口上限，模型切换请求也可能被 restart-guard 直接拒绝，导致该轮用户消息无法正常处理。

**原因：**

模型切换过程中，`session.requestHeader()` 仍然反映旧模型路由，而不是即将切换到的目标模型路由。

当前实现将摘要路由与目标模型路由进行比较。当二者不一致时，`guard()` 返回 `route-mismatch`，随后 pre-step 将 `skipped` 升级为 `reject`，导致请求在实际墙值检查之前就被拒绝。

现有 switch 测试用例大多显式配置了摘要模型，使摘要路由与目标路由一致，因此未覆盖默认配置下的这一情况。

**修复目标：**

- 使用目标模型的 context window 判断目标模型的上下文墙。
- 使用摘要模型自身的 context window 计算摘要预算。
- 不应仅因摘要路由与目标模型路由不同，就拒绝整轮用户请求。
- 增加默认 stock 配置下的模型切换测试，覆盖路由不一致的场景。

## P1：提前 prune 可能不可逆地改写健康会话

**影响：** 在会话尚未达到原生压缩触发阈值时，restart-guard 可能已经对 tool result 执行改写。

例如，在 `assumedRatio=2` 的配置下，守卫计算出的墙值可能显著低于原生引擎的实际触发阈值。健康会话在两者之间的区间内继续运行时，可能反复发生提前 prune。

由于这类改写具有不可逆性，可能在用户尚不需要恢复或压缩时就改变会话内容。

**修复目标：**

- 让 prune 与 compaction 共用一致的触发闸门。
- 不应仅因为假设墙值被提前触及，就对健康会话执行不可逆改写。
- 保留真正需要恢复或压缩时的必要处理能力。
- 增加测试，验证健康会话在未达到相应触发条件时不会被提前 prune。

## 当前状态

以上问题均已在本轮代码审查和针对性探针中发现，修复尚未完成。

本说明用于临时告知测试者当前已知问题，不代表所有其他边界条件均已验证。后续将更新修复版本及相应测试结果。
